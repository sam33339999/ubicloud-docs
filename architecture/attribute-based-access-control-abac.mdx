## 動機

身份驗證確認使用者的身份。授權則賦予這些使用者存取資源的權限。

Ubicloud 使用 [Rodauth](https://github.com/jeremyevans/rodauth) 進行身份驗證。對於授權，我們需要實作一個系統，讓使用者能夠靈活地存取雲端上不同雲端服務的各種資源。

目前，雲端授權的實作方式有很大的分歧。AWS、Azure 和 GCP 等超大型雲端供應商擁有強大的授權模型。其他雲端和託管服務提供商只有最基本的授權層級（使用者擁有或沒有專案存取權）。

Ubicloud 的授權旨在提供與超大型雲端供應商的身份存取管理（IAM）同樣強大的功能。它正在積極開發中，因此預計會有重大調整。

## 背景

現今雲端上有兩種常見的安全模型：角色型存取控制（RBAC）和屬性型存取控制（ABAC）。在 RBAC 中，管理員將使用者分配到角色中。然後在這些角色上定義對資源的權限。

例如，管理員將使用者「Enes Cakir」分配到「engineering」和「devops」角色。然後「devops」角色就可以存取生產資源並進行部署。

ABAC 更進一步，其中對資源的權限是根據屬性定義的。除了角色之外，屬性還可以包括使用者的位置、客戶端裝置類型或驗證方法等內容。例如，使用者「Enes Cakir」在歐洲時可以存取生產資源，但在美國時則不能。這確保組織可以定義靈活的政策以滿足其業務需求。

[Tailscale 有一篇很好的部落格文章](https://tailscale.com/blog/rbac-like-it-was-meant-to-be/)，更詳細地描述了安全政策、RBAC 和 ABAC。

所有三大超大型雲端供應商似乎都在向 ABAC 模型邁進。您可以在他們的網站上閱讀更多關於 [AWS](https://docs.aws.amazon.com/IAM/latest/UserGuide/introduction_attribute-based-access-control.html)、[Azure](https://learn.microsoft.com/en-us/azure/role-based-access-control/conditions-overview) 和 [GCP](https://cloud.google.com/iam/docs/conditions-overview) 的 ABAC 設計。這些設計依賴於條件表達式，比全新的 ABAC 設計更複雜。這可能是因為所有超大型雲端供應商都需要與其 RBAC 設計保持向後相容。我們希望在設計和實作上都提供更簡單的方案。

## ABAC 範例
在下文中，我們從一個 ABAC 範例開始並在此基礎上進行構建。下圖描述了一個簡單的場景，左側的使用者具有相關的「標籤」（經典角色），右側的資源也具有「標籤」。

![ABAC 1](/architecture/attribute-based-access-control-abac-1.png)

簡單的 ABAC 範例，其中使用者和資源具有相關的「標籤」
在 ABAC 術語中，主體是請求存取資源以執行操作的使用者。資源是主體想要存取的物件（例如 VM、簡單儲存桶或原始檔案）。操作是使用者嘗試對資源執行的動作。範例操作包括 VM 檢視、VM 建立、VM 刪除等。

除了三元組 `<主體, 操作, 物件>` 之外，我們引入了標籤的概念。我們可以將每個主體或物件與一個或多個標籤關聯。這四個概念為我們的授權模型提供了極大的靈活性。在上面的範例中，使用者或組織只需將正確的標籤分配給使用者和資源，即可建立細粒度的存取政策。

目前，Ubicloud 的標籤是由使用者分配的。我們沒有任何基於動態屬性（例如地理位置）的計算標籤。我們這樣做是為了從簡單開始，並根據實際客戶需求來發展我們的授權模型。

## 讓使用者無需擔心 ABAC

當然，大多數 Ubicloud 的新使用者不需要了解 ABAC。直覺上，在他們註冊後，他們應該能夠在 Ubicloud 上建立、檢視和銷毀資源。他們也應該能夠邀請其他使用者並在平台上與之協作。

為了實現這一點，我們引入了「超級標籤」的概念。下圖中的每個使用者和資源都有一個隱藏標籤，其中隱藏標籤與其相關的使用者或資源具有相同的名稱。這樣，使用者進入後，他們可以建立新資源並對他們建立的資源進行操作，而無需了解 ABAC。

![ABAC 2](/architecture/attribute-based-access-control-abac-2.png)

超級標籤為屬性提供隱藏名稱
「超級標籤」的概念還有一個附帶好處，就是能夠實現更細粒度的存取政策。例如，如果使用者「Enes Cakir」有 10 台虛擬機器，他想只授予「Daniel Farina」其中一台 VM 的權限，他可以這樣做。當然，Enes 可以透過為自己、Daniel 和 VM 建立標籤來做到這一點。超級標籤只是讓這個常見用例更加方便。

# 避免 ABAC 中的命名衝突

我們的 ABAC 範例的一個剩餘問題是命名衝突。不同的組織和使用者很可能建立相同名稱的標籤。例如，「prod」、「engineering」、「devops」、「database」等都是常見的標籤名稱。

為了避免命名衝突，我們使用命名空間限定每個標籤的名稱。然後我們使用這些完全限定的名稱進行授權。例如，在下面的範例中，Daniel 被標記為屬於 engineering 和 devops 組織。因此，他可以存取並將程式碼部署到開發和生產環境。另一方面，Enes 只被標記為屬於 engineering 團隊，因此只能部署到開發環境。

![ABAC 3](/architecture/attribute-based-access-control-abac-3.png)

命名空間限定標籤名稱並避免命名衝突
當然，我們不想用命名空間的概念困擾新的 Ubicloud 使用者。因此，當新使用者註冊時，我們為他們建立一個預設命名空間，並在該命名空間中建立他們的資源。然後他們可以透過邀請其他使用者並授予對其命名空間或資源的存取權限來更新他們的「專案」。

# ABAC 設計

我們的 ABAC 設計遵循這個簡單而強大的範例。我們所需要做的就是將上面介紹的概念對應到資料模型中。在我們的情況下，我們需要五個 PostgreSQL 表來實作雲端的 ABAC 授權模型。

![ABAC 4](/architecture/attribute-based-access-control-abac-4.png)

ABAC 設計的資料模型，該模型有五個 PostgreSQL 表
這五個 Postgres 表是：
1. 一個存取政策表，表示 `<主體, 操作, 物件>` 之間的關係。請記住，這裡的主體是使用者，物件是資源
2. 一個命名空間表，用於避免命名衝突
3. 一個存取標籤表，用於表示標籤（我們認為標籤這個名稱太通用，所以選擇了更具描述性的名稱）
4. 一個項目表，用於表示主體和物件
5. 一個應用標籤表 - 這是一個中間/樞紐表，我們用它來建立項目和標籤之間的多對多關係

## 130 行程式碼中的 ABAC 實作

將我們的 ABAC 概念對應到五個 PostgreSQL 表後，我們進行授權所需要的就是檢查從主體（由一個或多個標籤識別的使用者）到物件（由一個或多個標籤識別的資源）是否存在路徑。我們可以透過以下 SQL 查詢來執行此操作。

```sql
SELECT object_applied_tags.tagged_id, object_applied_tags.tagged_table, subjects, actions, objects
FROM accounts AS subject
   JOIN applied_tag AS subject_applied_tags ON subject.id = subject_applied_tags.tagged_id
   JOIN access_tag AS subject_access_tags ON subject_applied_tags.access_tag_id = subject_access_tags.id
   JOIN access_policy AS acl ON subject_access_tags.project_id = acl.project_id
   JOIN jsonb_to_recordset(acl.body->'acls') as items(subjects JSONB, actions JSONB, objects JSONB) ON TRUE
   JOIN access_tag AS object_access_tags ON subject_access_tags.project_id = object_access_tags.project_id
   JOIN applied_tag AS object_applied_tags ON object_access_tags.id = object_applied_tags.access_tag_id AND objects ? object_access_tags."name"
WHERE subject.id = :subject_id
   AND actions ?| array[:actions]
   AND subjects ? subject_access_tags."name"
```

這個查詢的好處在於：

- 它很強大。我們可以用這個查詢表達所有基於屬性的存取控制政策，用於使用者定義的標籤。
- 它有存在性證明。當您執行查詢時，如果它返回一個元組，主體就可以存取物件。如果沒有，主體就沒有授權。此外，您可以透過查看此查詢返回的元組來查看從主體到物件的所有存取路徑。
- 它很簡單。我們用 10 行 SQL 就獲得了 ABAC 實作。事實上，[實作我們授權政策的整個檔案](https://github.com/ubicloud/ubicloud/blob/main/lib/authorization.rb)只有 130 行程式碼。

當然，您可能會認為為每個授權操作執行 SQL 查詢不具擴展性。當我們達到這個規模時，我們會很樂意最佳化我們的實作，或者在需要時進行全面改造。到那時，我們也將對客戶存取模式有更深入的了解。在此之前，我們將擁有一個簡單的 ABAC 模型，其表達能力與 AWS、Azure 和 GCP 相匹配，採用開源實作。

## 結論

ABAC 提供了一種靈活的方式來授權使用者。有了它，組織和使用者可以表達使用者和資源之間的複雜存取關係。同樣重要的是，ABAC 比 RBAC 更簡單，簡單到無需太多努力即可掌握。Ubicloud 還具有不必像 AWS 或 Azure 那樣提供對 RBAC 的向後相容性的優勢。這些特性使我們能夠在幾個資料庫表中表達 ABAC 的資料模型，並在一個 SQL 查詢中實現核心實作。

我們也預期我們的 ABAC 設計會隨著時間而演進。如果您對此設計文件有任何問題或回饋，我們很樂意聽取您的意見。請在 GitHub 討論區開始對話，或透過 [info@ubicloud.com](mailto:info@ubicloud.com) 與我們聯繫。
